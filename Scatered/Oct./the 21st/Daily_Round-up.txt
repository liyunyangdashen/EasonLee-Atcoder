一、今日主战场：ABC 367 D
ABC 367 D — Pedometer
AtCoder · 400 分 · 环形数组与计数
AC

查看官方题目第一阶段：25 分钟，彻底卡住
下午你提交了训练反馈：
状态：卡住了；用时：25 分钟。

最初的问题不是不会写 C++，而是面对一个环形计数问题，不知道怎样突破二重枚举的时间复杂度。
当时我们约定：不直接给出完整解法，只进行分级提示。
随后，你拿出了第一份代码。
第二阶段：从环形到线性，自己建立暴力模型
你写了：
for (int i = 1; i <= n; i++)
    for (int len = 2; len <= n; len++) {
        int j = i + len - 1;
        if ((s[j - 1] - s[i - 1]) % m == 0)
            ans++;
    }


这是今天非常关键的起点。
因为你已经意识到：环形路径可以通过展开数组、建立前缀和来表示。
一开始程序还存在输入、前缀和复制和边界方面的问题，但算法模型已经建立。
你也立刻发现了最大障碍：
“可是这是 n 平方的。”
当 \(N=200000\) 时，最坏情况下二重枚举数量达到约 \(4\times10^{10}\) 次。
所以这份程序的 TLE 是可以预料的。
这一阶段的成果是：你知道怎样正确描述答案，但还不知道怎样高效统计答案。
第三阶段：开始从枚举转向余数计数
在看到前缀和同余的提示后，你写出了：
s[i] = (s[i] + s[i - 1]) % m;
h[s[i]]++;


随后尝试通过：
ans += h[i] * (h[i] - 1);


直接统计合法数对。
这一步比纯粹的二重枚举前进了一大截。
你开始不再关心每对站点具体走多少步，而是关心两个前缀和是否具有相同余数。
数学关系是：
\[
(S_j-S_i)\bmod M=0
\iff S_j\bmod M=S_i\bmod M
\]

但是，这个版本仍然错误。
为什么？
因为它把整个环上余数相同的位置放在一起统计，没有保证每个起点所对应的终点范围正确。
这也是今天最重要的概念性错误。
第四阶段：真正的瓶颈——窗口到底在哪里？
在解释静态余数统计的缺陷以后，我给出了滑动窗口的提示。
但你马上提出一个疑问：
“可是，窗口大小不一定啊。”
这个问题揭示了当时真正混淆的两件事：
- 两个站点之间的步数不固定；
- 但从一个固定起点出发，其他合法终点的数量固定为 \(N-1\)。
窗口维护的是终点前缀和的位置数量，不是物理路程长度。
于是：
\[
\text{窗口长度}=N-1
\]

当起点向前移动一个站点时，窗口也移动一个位置。
这一刻，你已经理解了为什么可以使用滑动窗口。
第五阶段：你自己写出了窗口更新
你回答：
h[s[i]]--;
h[s[i + n]]++;


删除位置是正确的，加入位置晚了一格。
我们进一步核对：
原窗口：
\[
S_i,S_{i+1},\ldots,S_{i+N-2}
\]

下一窗口：
\[
S_{i+1},S_{i+2},\ldots,S_{i+N-1}
\]

于是加入位置应该是：
h[s[i + n - 1]]++;


这解决了移动过程的边界问题。
第六阶段：从 WA 到 AC
你没有停留在理论讨论，而是继续修改代码并上传到 GitHub。
仓库中的最终代码包含：
h[s[n]]--;

for (int i = 1; i <= n; i++) {
    ans += h[s[i - 1]];
    h[s[i]]--;
    h[s[i + n - 1]]++;
}


这里有三条不变式：
1. 第 \(i\) 次查询前，h[] 统计恰好 \(N-1\) 个合法终点。
2. h[s[i-1]] 是当前起点对应的合法终点数量。
3. 每次查询后，删除旧窗口左端，加入新窗口右端。
最终实现无需线段树，也不需要每次重新计算所有终点。
复杂度的变化
最初暴力枚举O(N²)

最终滑动窗口O(N)


以 N=200000 计，核心枚举量从约 400 亿次降低到线性级别的窗口操作。另需 O(N+M) 的数组空间。

这次你给出的仓库版本明确标记了 AC，之后也确认已经通过。因此今日战绩记为 AC，不再无谓地反复追问。

当一个二重循环的外层变量增加 1 时，内层所需要的信息到底改变了多少？

有时不是全部改变。
